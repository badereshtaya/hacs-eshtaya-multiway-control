# Architecture

## Overview

Eshtaya Multi-Way Control is a Home Assistant **helper integration** with two independent event-driven engines sharing one administration surface.

```text
                      Eshtaya Control Center
                     /                       \
          Multi-Way Engine              Smart Group Engine
          /      |      \                /       |       \
      Output Controllers Virtual     Controller Members Virtual
```

The integration does not call vendor APIs directly. It coordinates entities already provided by Home Assistant integrations.

## Multi-Way engine

Each Multi-Way group has exactly one primary physical output, optional fallback output, one or more controllers and one virtual control entity.

### Rapid input pipeline

1. `async_track_state_change_event` receives an eligible source edge.
2. The edge enters a per-group FIFO queue.
3. Duplicate semantic reports may be debounced; opposite edges never are.
4. A transaction receives a unique sequence/id.
5. Latest physical authority is recorded.
6. The physical output is dispatched according to Instant/Balanced/Safe mode.
7. Reflective followers are synchronized without writing back to the active source.
8. Verification/retries run only while the transaction is still current.
9. Trailing reconciliation re-reads the source to defeat stale cloud echoes.

Every engine-issued service call uses a Home Assistant `Context`. Matching state changes are consumed as acknowledgements and never become new physical input.

## Smart Group engine

Smart Groups are intentionally independent from Multi-Way groups.

### Types

- **Physical**: one real controller drives all members.
- **Virtual**: a Home Assistant light/switch entity drives all members.

### Event serialization

State events are queued per Smart Group and processed in Home Assistant arrival order. Commands generated by the Smart Group engine carry dedicated Home Assistant Context IDs so their resulting state echoes are consumed.

### Aggregate state

- `any`: group ON when any enabled, non-quarantined member is ON.
- `all`: group ON only when all enabled, non-quarantined members are ON.

### Bidirectional mode

A member can become the source of a group command. A physical controller gets a short manual-authority window to prevent slower member/cloud reports from immediately undoing a wall press.

### Scene guard

When multiple members change inside the configured scene window, the engine treats the batch as an externally coordinated scene and adopts the resulting aggregate state rather than force-rewriting all members from the later event.

### Flapping and quarantine

Repeated abnormal state edges inside the configured window quarantine that entity for a bounded interval. Quarantined members are excluded from command fan-out and aggregate-state decisions. Admins can quarantine/release members manually from the Control Center.

## Persistence

Two versioned stores are used:

- `eshtaya_multiway.groups`
- `eshtaya_multiway.smart_groups`

Both reject future unsupported schemas. Smart Groups also store templates, project settings and bounded snapshots. Multi-Way stores bounded snapshots for undo.

A full backup bundles both stores. Full restore performs rollback if either store fails validation.

## Virtual devices and entities

Each logical group is represented as its own Home Assistant virtual device. Platforms dynamically listen for group configuration changes and add/remove appropriate control and diagnostic entities.

## Commissioning

The frontend reads Home Assistant Area and Entity registries, prioritizes compatible entities, offers Learn Mode and discovers native HA Group helpers. UI-created native Light/Switch Groups can be transactionally **taken over**: the original Entity Registry row is moved to a temporary rollback ID, an Eshtaya Smart Group claims and verifies the exact original entity ID, then Home Assistant removes the old Group Config Entry through the public Config Entry API. No Home Assistant `.storage` file is edited directly. If any pre-removal step fails, the original helper and entity ID are restored. Unsupported legacy/YAML/runtime group types remain read-only.

## Repairs and diagnostics

The Repair Center scans configured references against current Home Assistant states and supports atomic cross-engine remapping. Runtime failures may also create Home Assistant Repair issues.

Diagnostics report group policies, health and metrics without intentionally exposing activity source entity IDs.

## Security

The Control Center and configuration WebSocket API are admin-only. Runtime entities can be used normally by Home Assistant users according to Home Assistant permissions. Configuration Lock adds an application-level guard against accidental edits during/after commissioning.
